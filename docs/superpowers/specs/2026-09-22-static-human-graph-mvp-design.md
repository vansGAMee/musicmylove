# MusicMyLove: статический frontend и настоящий human graph

Статус: проект решения для проверки перед реализацией. Это не готовый MVP.

## Результат

Сохранить текущий интерфейс `src/components/MusicRecommender.tsx`, темы,
карточки, импорт и экспорт. Публичный Яндекс-плейлист импортируется одним
прикладным запросом браузера. Рекомендации и повторное ранжирование работают
в браузере на TypeScript. Vercel раздаёт только статические файлы.

Прямое требование пользователя разрешает офлайн audio embeddings вместо
старого запрета audio analysis. Запреты на LLM, Spotify как источник
рекомендаций и metadata-рекомендации сохраняются.

## Что есть в репозитории

- Next.js 16.3.5; установленное руководство подтверждает `output: 'export'`.
- UI использует `/api/search`, `/api/tastelift`, `/api/yandex/playlist`;
  обратная связь сейчас повторно вызывает сервер рекомендаций.
- `ml/tastelift-catalog.json`: 45 081 трек и 671 история, заявленный источник
  `listenbrainz-train-histories`. Векторы вычислены через `encode_metadata`.
  Эти векторы и старые веса не становятся новым human graph.
- В `data` нет аудиофайлов и исходных `real-profiles`. Старые истории могут
  помочь в локальной проверке интеграции, но не заменяют требуемую сборку из
  ListenBrainz dump с воспроизводимым происхождением.
- Изменение `next-env.d.ts` существовало до этой задачи и не относится к ней.

## Выбор архитектуры

1. **Выбранный вариант:** static export + отдельный маленький Node/TypeScript
   gateway с файловым кешем + офлайн сборщик. Это сохраняет UI и не требует
   базы данных или серверного инференса.
2. Полностью браузерный импорт напрямую из Яндекса потребовал бы проверки
   CORS и доступности всех upstream endpoints; на него не полагаемся.
3. Vercel API routes сохраняют текущую привязку к Functions и не соответствуют
   требованию пользователя.

Gateway должен размещаться там, где доступны Яндекс и выбранные источники
web context. Его регион сам по себе не доказывает доступность: нужен live
тест. Бесплатность отдельного хостинга и доступность из всех сетей РФ не
обещаются без проверки. Пользователь подтвердил: есть только Vercel,
отдельного сервера и готовой инфраструктуры нет. Поэтому реализация должна
включать готовый запуск gateway с нуля; выбор и подключение площадки остаются
обязательной частью выхода в production. Локально запущенный gateway не
считать выполнением требования публичного сервиса без установки у пользователя.

## Данные и офлайн сборка

### Human graph

Потоково читать официальный ListenBrainz dump, не загружать его целиком в
память. Сохранить checksum, дату, схему и сведения о выбранной части dump.
Разбить по пользователям до обучения; frozen test не использовать ни для
графа, ни для настройки коэффициентов. Связи — совместные прослушивания
в ограниченных временных окнах пользователей. Повторы одного пользователя
не должны многократно усиливать ребро. Снизить вклад сверхактивных
пользователей и популярных хабов. Получить нормализованные graph embeddings
из матрицы человеческих связей, например PPMI + truncated SVD с фиксированным
seed. Названия и жанры не участвуют в вычислении этих векторов.

### Настоящее аудио

Отдельный manifest сопоставляет recording ID, доступное аудио/preview,
источник, разрешённое использование и checksum. Офлайн encoder извлекает
векторы только из звука; первый кандидат — аудиоветвь LAION CLAP с закреплённым
checkpoint. Текстовый encoder не вызывается. Веса и исходное аудио хранятся
под игнорируемым `data/cache/`. Для отсутствующего аудио нет вектора и нет
sound score. Отчёт содержит реальное покрытие аудио.

Источник доступных preview ещё предстоит подтвердить на реальных треках.
Пустой manifest не считается выполнением требования audio embeddings.

### WEB-CONTEXT INDEX

Индексировать реальные публичные музыкальные страницы и tracklists с
явно извлечёнными парами artist/title. Хранить URL, дату и совместно
встречающиеся recording IDs. Общее присутствие на сайте или совпадение
жанра не создаёт связь. Навигацию и глобальные каталоги исключать.

Для отсутствующего в графе трека усреднять graph vectors подтверждённых
соседей с весами уверенности. Такой вектор помечается как временный web
context, а не как наблюдаемая человеческая история или аудио.

### Публикуемые артефакты

Versioned manifest с checksum и счётчиками покрытия; локальный нормализованный
track index; graph vectors + HNSW; audio vectors + отдельный HNSW; web context
shards. Согласованные версии ID и размерностей обязательны. Браузеру не
передавать исходные пользовательские истории. Загружать артефакты по мере
необходимости и кешировать по версии. Сборка HNSW детерминирована; поиск и
инференс в браузере — чистый TypeScript.

## Gateway: ровно две прикладные операции

`POST /playlist {url}` возвращает весь плейлист, artist/title и исходные IDs.
Допустимы внутренние пакетные upstream-запросы, но браузер не запрашивает
каждый трек. Проверять полноту результата: неполную HTML-выборку не выдавать
за целый плейлист. Разрешать только точные домены Яндекса и проверять redirect
targets; существующая проверка `hostname.includes('yandex.')` недостаточна.

`POST /context {tracks: [...]}` принимает все пробелы одним запросом. На
сервере нормализовать и дедуплицировать ключи, сначала проверить постоянный
файловый кеш; новые поиски выполнять с ограниченной конкурентностью,
тайм-аутом и числом попыток. Возвращать проверяемые URL и известные ID соседей.
Отрицательные результаты кешировать с TTL, ошибки upstream не считать
доказанным отсутствием. Одиночный batch HTTP-запрос не означает один запрос
к поисковому провайдеру. Провайдер и его реальные лимиты должны быть
подтверждены до заявления о рабочем web fallback.

Кеш gateway — `data/cache/`; без БД. Ограничения размера body, размера
плейлиста, частоты запросов, CORS для frontend origin. Секреты провайдера
остаются на сервере. Браузер сохраняет полученный context по версии и ключу.

## Браузер и TasteLift

1. Нормализовать полный плейлист и найти точные/проверенные aliases в индексе.
   Не сливать разные live/remix recordings без подтверждённой идентичности.
2. Для пробелов проверить статический web context, затем локальный кеш и
   один batch fallback. Не придумывать связи для оставшихся пробелов.
3. Отсортировать и дедуплицировать seeds перед построением heads. Выбрать
   2–12 детерминированных taste heads при достаточном количестве различных
   векторов; для единственного вектора использовать один head.
4. Искать по отдельным graph/audio HNSW, объединить примерно 2000 кандидатов.
   При меньшем каталоге не дополнять результат случайными треками.
5. TasteLift MVP — прозрачный детерминированный scorer: graph similarity,
   sound similarity при наличии, поддержка нескольких heads, редкие
   подтверждённые связи и новизна, штраф популярности и повторов артиста.
   Старые metadata-веса не переносить. Обучение новых весов — следующий этап
   после работающего сквозного пути, только на train/validation.
6. Исключить весь импортированный плейлист и известные positives, а не
   только первые 500 строк. Получить до 40 различных рекомендаций.
7. Like/dislike повторно ранжирует сохранённый пул в Web Worker без сети;
   учитываются только явные dislike. Отсутствие лайка не означает negative.

При недостатке данных показать фактическое покрытие и понятное состояние
в существующем UI. Демонстрационные карточки не выдавать за персональный
результат. Поиск в UI перевести на локальный индекс. Сохранить разметку и CSS
настолько, насколько позволяет замена источника данных.

## Последовательность реализации

1. Контракты артефактов, сборщик графа и реальный небольшой dump sample;
   TypeScript retrieval/ranker с тестами инвариантов.
2. Gateway импорта, проверка реального публичного плейлиста, подключение
   сохранённого UI к локальному worker; static export без API routes.
3. Реальные audio embeddings и HNSW, WEB-CONTEXT INDEX и пакетный fallback.
4. Проверки, покрытие и deployment инструкции; live проверка выбранного
   gateway и клиентского пути из РФ перед утверждением о доступности.

Пункты 1–2 — промежуточная сквозная проверка, не завершение всей задачи.

## Приёмка

- В deploy output нет Functions; браузер не вызывает старые `/api/*`.
- Один прикладной запрос импорта; максимум один context batch для всех
  пробелов; повторный прогон использует кеш; feedback не использует сеть.
- Проверяются перестановки и дубликаты seeds, exclusion всего плейлиста,
  отсутствие вымышленных audio vectors, graph-only и audio-only случаи,
  нехватка покрытия, испорченные shards, тайм-ауты и неполный импорт.
- Отчёт содержит источник dump, число пользователей и треков, audio/web
  coverage, размеры загрузки, время получения рекомендаций и rerank.
- Выполнить `npm test`, `npm run typecheck`, `python -m pytest`,
  `python scripts/check_parity.py`, `npm run smoke:live`, `npm run build`.
  Старый smoke сейчас проверяет прежний серверный пайплайн: обновить его
  для нового сквозного пути, не подменять live тест mock-ответами.
- Сравнить UI до/после; отдельно проверить на реальном публичном
  Яндекс-плейлисте через размещённый gateway. Локальные тесты не доказывают
  доступность сервиса из РФ.
